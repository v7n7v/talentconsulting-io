# Account utilities: source audit and upgrade recommendations

Audit date: 2026-09-28. Read-only source review in `Taco-upgrade`: all ten Settings tabs, Upgrade and standalone Feedback. No application edits, account actions, payment sessions, email sends, credentials, provider calls or tests executed. Browser observations belong to the parent audit. This is a bounded implementation/product review, not a full legal, privacy, security or billing assurance audit. P1 means fix before wider real-data use; P2 means follow-on usability/completeness. No P0 incident was established.

## Decisive utility findings

### U01 — P1: Profile silently drops two editable fields

Phone and Bio initialize to blank local state (`app/suite/settings/page.tsx:607-608`); both appear editable (`:678-695`). Save only passes `{displayName}` to `authHelpers.updateProfile` and then shows “Profile updated!” (`:612-619`). That helper accepts only displayName/photoURL and calls Firebase Auth (`lib/firebase.ts:406-413`). This is directly established from code, not inferred from an unobserved backend. Preserve all supported profile fields or remove the unsupported inputs. Save/reload and error injection must prove no accepted text is silently lost.

### U02 — P1: Push settings are cosmetic; email load failure is rendered as state

The push keys are initialized true (`settings:1044-1046`), but `toggle` only has a jobs-preference path and a map of email keys (`:1085-1137`). Push changes therefore never reach any persistence request in this UI. Separately, non-OK email/preferences loads become empty objects (`:1059-1060`), defaulting every email toggle false; network errors are swallowed (`:1073`). A false-looking switch can mean “couldn't read,” not “off.” The load also lacks an owner/request completion check. Retire cosmetic controls; introduce loading/unavailable/confirmed/pending states with server read-back and owner binding.

### U03 — P1: Feedback accepts 5,000 characters but stores only 2,000

Both forms advertise/allow 5,000 (`app/suite/feedback/page.tsx:361-367`; `settings:1515-1521`). The API validates that bound (`app/api/feedback/route.ts:49-53`) and then silently sets `safeMessage = message.slice(0,2000)` before persisting (`:64,75-83`). Message shortening for an email summary can be valid; shortening the canonical customer report is data loss. Preserve the full accepted text; truncate only labeled delivery summaries, or make 2,000 the explicit shared input limit. Add boundary tests and a receipt that proves the persisted text matches what the user sent.

### U04 — P1: account lifecycle copy extends beyond the confirmed implementation

Settings says deactivation temporarily hides the profile and pauses all email notifications (`settings:1694-1695`). The confirmation route sets `accountLifecycle.status`, optional communication preferences and job email flags (`app/api/account/lifecycle/confirm/route.ts:37-63`), then emits a deactivated email (`:87-94`). A scoped search found no account access/profile consumer of the `accountLifecycle` record. The email itself asserts the profile is no longer active (`lib/email/catalog.ts:529-531`). Therefore profile-hide/access enforcement is **unverified and not evident in the inspected code**, not demonstrated by the state write. Transactional/security mail should also be distinguished from optional mail.

Deletion is not immediate: the route deliberately queues an operations request to finish approved retention/deletion processing (`confirm:73-75`), and the confirmation page truthfully says queued (`app/account/action/page.tsx:71`). Keep that safe distinction. Add request status, operator completion receipt and recovery for token-consumed/processing-failed states; implement or explicitly narrow deactivation and reactivation behavior. Do not claim data was deleted at confirmation. No deletion was executed in this audit.

### U05 — P2: Help and Settings drift from the actual product

Help promises session enumeration/revoke (`settings:2130`) while Sessions says unavailable (`:1605-1617`), calls the default theme dark (`:2175`) while ThemeProvider starts System (`components/ThemeProvider.tsx:46`), and uses old names such as Liquid Resume (`settings:1921-1922`). The profile description advertises avatar management (`:35`) while this form renders only an initial and no avatar action (`:636-655`). Consolidate shared feature descriptions and avoid help content that turns incomplete controls into promises. Acceptance: a documentation walkthrough can complete every claimed capability, with unavailable features explicitly marked.

## Upgrade order and verification boundaries

1. Correct false completion and data-loss cases first: export stub, dropped profile fields, decorative push toggles, truncated feedback, lifecycle/help claims.
2. Reuse the privacy controls' owner/request-generation pattern for profile, AI safety, notifications, billing state and support. Load failures must not look like saved defaults.
3. Consolidate Feedback/Contact and navigation/deep-link behavior; retain one support receipt model and explicit diagnostics consent.
4. Implement remaining account lifecycle/export/session capabilities only as complete server-backed workflows, with request/status/recovery and verified completion.
5. Run isolated staging matrices for auth, email, MFA, subscriptions, cancel/resume, webhook sync, analytics withdrawal, diagnostics revoke and lifecycle processing. Billing existing tests cover valuable ownership/recovery invariants, but no payment/entitlement safety claim follows from this source inspection alone.

Existing focused test files include `scripts/email-account-actions.test.js` (signed/expiring/non-destructive confirmation intent), `scripts/stripe-account-selection.test.js`, `scripts/stripe-checkout-reconciliation.test.js`, `scripts/stripe-checkout-economics.test.js`, `scripts/stripe-checkout-customer-write.test.js`, `scripts/stripe-webhook-envelope.test.js` and `scripts/stripe-staging-resume-canary.test.js`. They were inventoried, not executed in this audit. Public `/tools` entries are explicitly left to the parent source/browser inventory rather than counted as deeply reviewed here.
