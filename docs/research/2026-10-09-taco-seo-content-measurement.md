# Taco SEO content quality, conversion and measurement brief

**Research date:** 9 October 2026  
**Scope:** Public content quality, evidence/authorship, internal links, conversion path, and privacy-safe measurement. This is an implementation brief, not a traffic forecast.  
**Checkout inspected:** `/home/xwingace/Documents/Projects/Taco-upgrade`  
**Live review:** public templates page and auto-apply article were readable through public HTTP/web results on 9 October. Some other direct public URLs were unavailable to the browser reader; source review establishes what the current checkout renders, not current production state for those routes.

## Decision

Fix accuracy and trust before expanding the page inventory. The largest content risks are unsupported hiring/ATS statistics, invented resume achievements presented as examples, claims that conflict with the actual resume workflow, stale/unsourced model and privacy claims, and structured dates that do not represent editorial revision history. These matter more than adding another batch of role pages.

The current content library has 15 generated role/industry pages (5 resume examples, 5 keyword guides, 5 interview guides) plus 7 blog posts. The main SEO component gives these pages a consistent CTA and related-tool frame, but it cannot supply evidence, role-specific utility, or accurate lifecycle information by itself. Start with a factual correction pass, then publish three small, evidence-backed guides. Do not invent ranking, conversion, hiring, or product-outcome targets while Search Console and Analytics property data remain unavailable.

## Evidence labels

- **Observed:** found in checked source or readable live page output. Source facts below are from the checked-out files as of 9 October; local code may be ahead of production.
- **Risk:** an observable statement could mislead a job seeker or conflicts with the documented/source-backed product boundary. This does not establish that a person was harmed.
- **Hypothesis:** a content, link, or event change worth validating after establishing a real baseline.
- **Unknown:** requires owner-authorized Search Console/GA4 access, production inspection, or editorial/product fact-check; do not substitute zero.

## Internal links and the conversion journey

### What exists

- `PublicSeoPage` gives the three guide families shared navigation, hero primary/secondary CTAs, three “Use this guide with” links, a lower CTA, a second related-links card, and a source-context area ([`PublicSeoPage.tsx`](../../components/seo/PublicSeoPage.tsx#L38)). The default related links point to public resume builder, ATS analyzer and interview prep pages, with templates offered lower down ([`RelatedLinks.tsx`](../../components/seo/RelatedLinks.tsx#L11)).
- The resume-example route sends readers to public builder and templates. Keyword pages send readers to public analyzer and builder. Interview-question pages send readers to public interview prep and builder. Templates links back to role examples and keyword guides. The readable public templates page confirms related example/analyzer links and a separate free/Standard template callout.
- Public tool pages then route into the signed-in workspace, e.g. `/tools/resume-builder` → `/suite/resume`. The private workspace is the correct place for a user's resume/job data; public pages must not serialize or expose private drafts.
- The shared guide page also promotes `/tools/ai-humanizer` and `/suite` from a generic bottom callout. Those CTAs are not equally relevant to a resume example, keyword guide, and interview guide; `/suite` also jumps from education to an account gate without explaining it.

### Conversion recommendations

1. Let the page's task determine the next click. Resume example → resume builder or a relevant template; keyword guide → ATS analyzer, then resume builder; role interview guide → interview practice. Keep one primary CTA, and make the account/plan gate clear before the user enters `/suite/*`.
2. Describe the actual next-step behavior in CTA labels: “Compare this job description with your evidence,” “Choose a template,” or “Practice this question.” Avoid “pass,” “get hired,” “land the job,” or an assumed upload/save unless the destination actually permits that action.
3. Add contextual links in article text to the one source or public tool that completes that subsection. A repeated “related tools” component is useful for discovery but cannot replace sentence-level links or a step-by-step handoff.
4. Keep informative paths crawlable and public. Keep personal result routes, saved resume names, job/company details and document state in authenticated/noindex workspace routes. A public CTA can link to the suite; it must never put resume, job-description, query, or user-identifying values in its URL.
5. Treat internal-link changes as user navigation first; do not add exact-match anchors to every page or generate many near-duplicate role pages. Maintain one canonical public owner for each task family.

### Recommended task graph

```text
role/industry guide ──> public matching/builder/interview page ──> signed-in workspace
        │                          │                                   │
        └──> relevant template      └── explain gate + privacy          └── review → export/save
```

This is a hypothesis for reducing “dead end” guide visits. Validate with consented, coarse CTA-to-workflow counts and Search Console page outcomes, never by joining query text or resume content to an individual.

## Editorial pilots (three, with review gates)

Each brief is a single task with an evidence trail; these are not permission to generate programmatic role variants.

### 1. Tailor a resume to a job description without inventing evidence

- **Intent / proposed home:** the current sole tool owner for builder/tailoring is `/tools/resume-builder`. A supporting how-to guide can teach evidence mapping and link into that section, but it should inform the tool page rather than compete with it as another tool route or target the same task query. Rewrite relevant resume-example/keyword content as supporting material; do not add `/tools/resume-tailoring` now. Consider a separate route only after Search Console/query or reader-task evidence records a distinct intent, the page has unique reviewed content and a real product demo, and a clear non-competing link/gate is defined.
- **Reader outcome:** mark each job requirement as supported by source, adjacent/transferable, or missing; choose whether to re-order, clarify, or leave the resume unchanged; review every change before export.
- **Outline:** (1) extract named job requirements from the real posting; (2) map each to a resume source line or a clearly missing-evidence state; (3) adjust wording only where the source supports it; (4) present a bracketed `[verified result]` scaffold rather than made-up metrics; (5) compare original and proposal; (6) check the selected document/export; (7) a one-page truth checklist.
- **Evidence / citations:** cite the user-supplied job post as the immediate source of employer-specific requirements; cite a relevant O*NET occupation profile for general tasks/skills and BLS Occupational Outlook Handbook for occupational context only. Cite Google's people-first guide for authorship/evidence standards if discussing how Taco creates the guide. Do not use general labor-market pages to substantiate ATS behavior.
- **CTA / internal links:** public Resume Builder → `/tools/resume-builder`; public templates → `/templates`; only after explanation, signed-in Resume Studio `/suite/resume`. Return to analyzer if user has a target JD; no auto-apply CTA.
- **Review gate:** product owner verifies actual screen-by-screen handoff and guardrail state; resume subject reviewer checks examples for false facts; editor checks sources, author, dates and plain-language claim boundary. No example results without source evidence.

### 2. What a resume match score can and cannot tell you

- **Intent / proposed home:** education owned by `/tools/ats-analyzer`, with one supporting article link from ATS-related content. Keep analyzer UI/interactive task primary.
- **Reader outcome:** understand what the product measured, what fields influence the displayed result, what is parser/readability guidance versus job-description overlap, and why a score cannot predict employer screening/interview outcome.
- **Outline:** (1) publish actual score inputs with an example produced from a reviewable test fixture; (2) explain each category and scoring boundary; (3) demonstrate one meaningful change and one unmatched requirement; (4) state vendor/employer variance and all excluded signals; (5) offer a printable pre-submit checklist; (6) collect corrections when code changes.
- **Evidence / citations:** score source code and a repeatable local/fixture walkthrough are the evidence for Taco behavior; link an identified ATS provider's first-party parse guide only for that provider's behavior. O*NET can support occupational-task context, not the score. EEOC's selection-procedure guidance provides context that employer selection tests are procedures with employer-specific validity/legal considerations; do not stretch it into an ATS feature claim.
- **CTA / internal links:** public ATS Analyzer stays primary; link the resume tailoring workflow only when the next step is supported; templates page for format/readability. CTA says “Review keyword and structure guidance,” not “pass the ATS.”
- **Review gate:** data/product owner approves the score formula and excludes any unexplained feature; QA confirms screenshots/output are from the current route and score version; legal/product review the caveat and no-employer-prediction statement. Update substantive modified date only after this review.

### 3. Build an interview story bank with STAR without writing fictional answers

- **Intent / proposed home:** improve `/interview-questions/[role]` template for one role pilot, then retain only if a role-specific task differentiates from its siblings.
- **Reader outcome:** collect actual stories, label the candidate's contribution and evidence, identify an unresolved metric as unknown, and practice a concise answer without memorizing a generated script.
- **Outline:** (1) select a job-ad requirement; (2) capture a real situation/task/action/result with a “what I can verify” row; (3) make role-neutral story reusable across two question types; (4) ask a follow-up on tradeoffs and learning; (5) use a “result not measured” option rather than inventing numbers; (6) create a 10-minute practice routine.
- **Evidence / citations:** use O*NET tasks for occupational context and its explicit distinction between occupationally specific tasks and broad work activities. Use CareerOneStop interview material if editorial review confirms the exact page and advice remain current. Do not claim “most common” questions or predict interviewer scores without original evidence.
- **CTA / internal links:** role guide → `/tools/interview-prep` to practice; link one relevant resume example only if it teaches a source-evidence step. Explain that AI feedback is practice guidance and not an employer's evaluation.
- **Review gate:** a named editor/qualified reviewer validates the role lens; no invented candidate persona, score, answer outcome or guaranteed interview; product owner verifies the destination does not describe feedback as selection prediction.

## Measurement foundation and privacy boundary

### Current state (observed)

- `ConsentAwareAnalytics` does **not** load GA4 from the server layout. It starts disabled and refreshes authenticated consent from `/api/observability/consent`; the stored grant must match the current notice version and server collection policy. Consent refreshes on auth, visibility, focus and a five-minute timer; a revocation broadcast sets pending revocation, disables collection and clears `_ga*` cookies ([`ConsentAwareAnalytics.tsx`](../../components/privacy/ConsentAwareAnalytics.tsx#L23), lines 24–116 and 118–161).
- `lib/analytics.ts`'s normal `track` helper checks both `window.gtag` and `hasProductAnalyticsConsent()`, then passes the event through `sanitizeGa4Event` ([`analytics.ts`](../../lib/analytics.ts#L32)). The sanitizer is event-specific and drops unknown/raw keys; existing events keep `sona_*` names and a compatibility API to avoid a blind rename ([`ga4-privacy.ts`](../../lib/analytics/ga4-privacy.ts#L18), lines 257–end).
- Existing `scripts/analytics-privacy-contract.test.js` covers default-denied state, ignores browser-persisted grants, sanitizes injected email/URL/job identifiers, verifies that GA4 only loads through the consent-aware component, checks withdrawal/reset clears consent early, and rejects raw search/company/title/resume IDs from the analytics facade (lines 46–176). `scripts/upgrade-funnel-analytics.test.js` checks current checkout events. Do not weaken either contract.
- Server-side observability is a separate consent-controlled path. Event schemas are strict and bound allowed fields; forbidden keys include uid, email, resume/document/JD/title/company/search text, URL, IP, credentials and raw metadata (`lib/observability/contracts.ts:45–144`). Server ingestion is authenticated, rate limited, consent-rechecked, idempotent by operation and disabled unless production readiness checks pass (`app/api/observability/events/route.ts:24–72`, `lib/observability/recorder.ts`, `lib/observability/config.ts:28–143`). The existing product analytics consent is optional and defaults false (`lib/observability/consent.ts:23–31`). Retention policy and secret readiness are explicit prerequisites; SEO should not silently repurpose reliability/diagnostic telemetry.
- Two gaps are directly relevant: `SeoTrackedLink` invokes `window.gtag` directly with `page_path: window.location.pathname` and `link_url: String(props.href)` rather than the central consent/sanitizer facade ([`SeoTrackedLink.tsx`](../../components/seo/SeoTrackedLink.tsx#L19)); and the global GA4 config has `send_page_view: true` ([`ConsentAwareAnalytics.tsx`](../../components/privacy/ConsentAwareAnalytics.tsx#L138)). The tag is currently consent-gated, so this is **not evidence of an observed disclosure or PII leak**. It is a source-level gap because GA4's default `page_location` is the current URL and default `page_referrer` is the browser referrer; an application query/path or referrer can therefore enter tag collection unless controlled. The signed-in resume handoff route already manipulates a `pendingResume` query parameter (`app/suite/agent/page.tsx:1676–1684`), illustrating why exact route allowlisting and query-free page measurement are required.
- The current funnel has `sona_resume_upload_started`, `sona_resume_parsed`, and `sona_resume_saved` events; `tool_use(tool='resume_morph')` follows a valid accepted morph result; `resume_download` fires after the document builder/download function returns successfully. There is no explicit “JD ready,” review decision, template selection or save-vs-export funnel event in the current `analytics.ts` facade. Do not infer those conversions from a CTA click or an API request.

**Implementation guardrails:**

1. Route every event through one facade that calls `hasProductAnalyticsConsent()` and `sanitizeGa4Event()`. `SeoTrackedLink` must pass only fixed enumerations and must not access/send `window.location.pathname` or the href as analytics values. The currently loaded tag is a transport, not an authorization check.
2. Disable implicit `page_view` and any Enhanced Measurement history page changes if query-bearing app paths can be included. If page counts are needed for authenticated consenting sessions, manually send a `page_id`-derived canonical URL/title from a finite route registry; exclude query, hash and raw referrer, and do not include private workspace routes in SEO page-level reports. Confirm GA4 property Enhanced Measurement settings before asserting the code alone is sufficient. The GA4 docs state `page_location` defaults to `document.location`, `page_referrer` defaults to `document.referrer`, and pageview sends by default; these are configuration inputs, not evidence that PII was sent here.
3. Use per-operation local dedupe/state transitions for attempts and successes; server operation IDs can dedupe server observability records but must not be exported to GA4. Do not make retries emit multiple “success” counts for one completion. Errors are fixed buckets; no exception text.
4. Keep product-funnel events strictly opt-in. No GA4 loaded, cookies, request or event when consent is absent, stale, disabled by server policy, or revoked. ### Acceptance tests and operational review

Extend the existing privacy-contract test (or a focused companion) rather than creating a second analytics system. Cover: denied-by-default; an injected `window.gtag` does not bypass denial; verified consent emits one allowlisted event; stale notice/server collection disabled sends none; revocation immediately disables events and clears first-party GA cookies; consent re-grant only after current server confirmation; `?pendingResume=`, `?email=`, fragments, arbitrary paths, raw external referrer, malicious `props.href`, email/phone/URL in CTA props never appear in outgoing payload; unknown event/enum drops or falls back to a fixed category; success events only happen after actual accepted completion; failed, cancelled, superseded and duplicate operations do not increment success; template and review rerenders do not duplicate.
