# Agent orchestration and durable execution for Taco

**Research cutoff:** 2026-10-08. Vendor documentation is rolling and most cited pages do not publish a stable revision date; sources were checked for this cutoff. No post-cutoff material is used.

## Recommendation

**Proposed:** Keep Taco’s existing TypeScript workload harness and make Firestore the canonical job state. Use the current Cloud Run/cron path for bounded work, and add Cloud Tasks only where work needs queueing, rate control, delayed retry, or reliable dispatch beyond a request lifetime. Model a run as explicit, versioned steps with durable status and idempotency keys. Keep model calls behind Taco’s existing provider adapter. Use one coordinator for most user-facing work; permit parallel specialists only for independent, bounded subtasks with typed outputs and a clear merge step.

Do not adopt a second agent framework and a durable workflow engine together. If Taco needs a cleaner in-process reasoning/tool loop, **Vercel AI SDK 6 `ToolLoopAgent` is the smallest provider-neutral TypeScript option to evaluate**; it offers bounded loop controls and model switching, but does not supply durable jobs. OpenAI Agents SDK JS offers managers, handoffs, guardrails, and tracing, but is a runtime abstraction rather than the job store or scheduler. OpenAI's newer hosted Agents API is materially different: it provides a managed Codex harness, sessions, orchestration, recovery, sandbox, and subagent delegation. It is worth evaluating for sandboxed coding/research tasks, but Taco should validate fit for career workflows and account for OpenAI coupling. LangGraph is the strongest fit if product workflows become explicit state graphs with review pauses and resumable state, though it adds a second state model/checkpointer. Temporal is the escalation choice for long-lived, multi-step jobs that must survive deploys/restarts and wait on signals or approvals with strong operational guarantees; its worker/service model is a larger infrastructure commitment. Google Workflows can orchestrate GCP services and callbacks, but would move product flow control into a GCP-specific definition. Responses API background mode can let an OpenAI response continue beyond a synchronous HTTP request, but it is provider-specific request continuation, not Taco's job ledger or a general workflow runtime. OpenAI Agent Builder is a separate legacy product; the current docs say it is scheduled to shut down on 2026-11-30, so do not start new product work there.

Anthropic's Claude Managed Agents is now a real managed-runtime option, not just a design pattern: as of the cutoff its official docs mark it beta and position it for long-running asynchronous agent work. It offers a durable server-side session/event history and managed harness/environment, with self-hosted sandbox options. This can save substantial harness and runtime engineering, but binds the agent execution/session layer to Claude/Anthropic and comes with beta/data-retention constraints. Treat it as a candidate for a Claude-centered long-horizon product feature, not as a provider-neutral runtime. Anthropic's published “session / harness / sandbox” separation is still a useful architecture boundary even if Taco does not adopt its hosted service. [Anthropic architecture article](https://www.anthropic.com/engineering/managed-agents) · [Managed Agents overview](https://platform.claude.com/docs/en/managed-agents/overview)

This recommendation is an **architecture proposal**, not a claim that these components are currently implemented. The supplied baseline is Next.js 16 / React 19, TypeScript, Firebase/Firestore, Cloud Run/cron, and an existing bounded AI workload harness; the code-level harness audit is separate work.

## Single agent vs. fanout

Use a single coordinator by default when work is sequential, shares context, or needs one final accountable result. “Agentic” should mean the model can choose among a bounded set of actions and iterate where that helps, not that every task gets a graph or multiple personas. Fan out when tasks are actually independent (for example, separately scoring a role against a résumé and drafting a networking note), have clear output schemas, and can run concurrently. Persist each branch, cap the branch count and token/time budget, and have deterministic code merge or reconcile results. For open-ended research, a manager that keeps final-answer ownership is easier to constrain; a handoff is appropriate when a specialist should own the rest of a turn. OpenAI’s orchestration guide describes these patterns and notes that code-driven chains/parallel calls are more predictable in cost, speed, and behavior than leaving all routing to a model. [OpenAI agent orchestration](https://openai.github.io/openai-agents-python/multi_agent/)

Fanout multiplies model/tool calls, latency variance, and partial-failure handling. Do it when measured quality or wall-clock time justifies those costs; do not use “multi-agent” as a proxy for autonomy.

## State ownership and failure semantics

**Proposed ownership:** Firestore remains the user-visible source of truth: job status, owner/user, workflow version, step attempts, outputs or references, approval request/result, timestamps, and terminal error. Queue messages carry a job ID and step/version key, not the whole canonical state. Cloud Tasks is a delivery mechanism, not the record that a job completed. Cloud Run handlers execute one bounded step and write its result/state transition before acknowledging the task. UI progress reads from Firestore.

Create the job/step intent in a Firestore transaction, then enqueue by stable task name or through a small outbox/dispatcher. A transaction cannot atomically include Cloud Tasks or a model/provider call. If the process crashes after Firestore commit but before enqueue, the dispatcher must find pending work; if it crashes after enqueue but before recording dispatch, retry may enqueue/execute again. Cloud Tasks is at-least-once, and task-name deduplication is time-bounded, so handlers need application-level idempotency. Firestore transaction callbacks themselves may be retried; they must contain only deterministic reads/writes, never model calls or external effects. [Cloud Tasks delivery semantics](https://docs.cloud.google.com/tasks/docs/dual-overview) · [Firestore transactions](https://firebase.google.com/docs/firestore/manage-data/transactions)

Use a stable idempotency key such as `jobId/workflowVersion/stepName/inputRevision`. Claim a step with a transaction/lease; persist attempt count and lease expiry; on retry, detect a committed step result and return it. For external writes (email, application submission, profile update), use the destination’s idempotency key where available or a durable “effect intent / effect completed” record with reconciliation. No queue, checkpoint library, or workflow engine can guarantee exactly-once effects across a database and an unrelated external service without cooperation from that service. Prefer at-least-once execution plus idempotent effects and reconciliation.

Human approval is a persisted state transition (`awaiting_approval` → `approved`/`rejected`), authenticated and authorized in the app, with a unique approval request ID. Do not hold a Cloud Run request open while waiting. Approval should enqueue the next step or mark it resumable. If Taco later uses LangGraph interrupts or Workflows callbacks, keep the Firestore approval record authoritative and treat runtime resume as a command that can safely be retried. Google Workflows callbacks can wait for external requests, but the callback endpoint is scoped to that workflow execution. [Workflows callbacks](https://docs.cloud.google.com/workflows/docs/creating-callback-endpoints?hl=en)

## Incremental adoption path

1. **Keep existing harness.** Write down job/step states and invariants; persist workflow version, attempt count, timestamps, output references, and error class. Add idempotency around each external side effect. Keep bounded synchronous work synchronous.
2. **Queue only what needs it.** Use Cloud Tasks for burst control, rate limits, scheduled retries, or work that must outlive HTTP. Dispatch small ID payloads to authenticated Cloud Run endpoints. Add an outbox/repair scan so Firestore intent cannot be stranded if queue creation fails.
3. **Add explicit fanout narrowly.** Launch a small set of independent specialist calls, each with its own status and typed result; set concurrency/token/time limits; merge deterministically and handle one branch failing without repeating successful branches. Measure completion time, quality, retries, token spend, and user benefit.
4. **Adopt one heavier runtime only at a trigger.** Choose LangGraph if product needs graph-shaped state inspection and human pauses; choose Temporal if jobs are long-running, must survive deploys reliably, involve many timers/signals/compensations, or the team spends more engineering effort rebuilding retry/replay/visibility than operating Temporal. Use Workflows where the process is chiefly GCP service orchestration. Migrate one workflow, keep Firestore as product-facing record, and avoid two competing workflow authorities.

## Adoption trigger

Revisit this decision when at least one real workflow regularly spans multiple deploys or user wait periods, needs pause/resume/compensation across several services, or has enough duplicate/lost/replayed work that custom Firestore + queue recovery is a recurring reliability burden. Track actual failure recovery time, duplicate side effects, stuck-job rate, manual repair hours, median/p95 latency, and provider spend. A complex agent graph without those needs is not itself a trigger.
