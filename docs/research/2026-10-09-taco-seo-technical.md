# Taco SEO technical research and implementation plan

**Research date:** 9 October 2026  
**Scope:** source inspection plus unauthenticated requests to `https://talentconsulting.io` and official Google Search Central / Next.js docs. No authenticated, user, resume, or account data was requested or accessed.  
**Purpose:** evidence-led technical SEO implementation plan for Taco. Implementation order and ownership align with the canonical [Taco SEO upgrade plan](/home/xwingace/Documents/Projects/Taco-upgrade/docs/taco-seo-upgrade-plan.md:91): S0 deterministic fixtures/config first, then S1 metadata-only corrections after coordinator ownership is assigned. This is a research brief; no product source files were changed.

## Findings that should shape the work

The canonical host is already consistently enforced at the edge: HTTP and `www` each returned one `301` to `https://talentconsulting.io/`; the apex HTTPS homepage returned `200`. The public sitemap and robots file both returned `200`. The current sitemap has 35 absolute apex URLs and the full repository audit crawled all 35 successfully. This gives Taco a sound discoverability baseline.

The most consequential defect sits outside that sitemap inventory. On the live site, `/privacy`, `/terms`, and `/suite` return `200` but emit `rel=canonical` to `https://talentconsulting.io` and `robots=index, follow`. The common cause is the root canonical at [app/layout.tsx](/home/xwingace/Documents/Projects/Taco-upgrade/app/layout.tsx:58), which child pages inherit unless they override it. Privacy and Terms declare their own titles and descriptions but no canonical in [app/privacy/page.tsx](/home/xwingace/Documents/Projects/Taco-upgrade/app/privacy/page.tsx:6) and [app/terms/page.tsx](/home/xwingace/Documents/Projects/Taco-upgrade/app/terms/page.tsx:5). `/suite` has a client layout and no `robots` metadata ([app/suite/layout.tsx](/home/xwingace/Documents/Projects/Taco-upgrade/app/suite/layout.tsx:1)); suite children are not uniform: a second live check found `/suite/resume` self-canonical but indexable (`index, follow`, including Googlebot), while the `/suite` root inherits the homepage canonical. Both are disallowed by `/robots.txt`. This is an index-control inconsistency, not evidence that private data was returned or indexed. `/settings` and `/auth/reset-password` emit noindex while their paths are blocked. Google cannot read noindex behind a robots disallow; a blocked URL may still be indexed from external links. First classify route behavior: preserve crawl blocks for routes that must stay inaccessible and require server-side authentication for private data; for any anonymous public shell whose only exclusion is search visibility, allow crawling just enough for crawlers to read noindex. Do not treat robots as access control or remove private crawl blocks wholesale. [Google’s noindex guidance](https://developers.google.com/search/docs/crawling-indexing/block-indexing) (accessed 9 Oct 2026).

The current SEO audit is useful but not a release guard for these defects. `scripts/seo-audit.js` does detect a canonical that differs from a fetched URL (lines 467–484), but it only fetches sitemap URLs (lines 834–864). The 35-URL live sitemap excludes `/privacy`, `/terms`, and all `/suite` paths, so the audit never evaluates them. The CI mode exits unsuccessfully only if there is a **critical** issue (lines 943–945); canonical issues are medium, and the scheduled workflow therefore reports green for a route-level canonical regression. The fresh full run found **0 critical, 0 high, 22 medium, 1 low**. Its “20–70 character title”, “70–170 character description”, and fixed word-count thresholds are local heuristics, not Google eligibility rules. Keep these as review signals unless a product-specific, measured reason supports a hard gate.

The sitemap’s static `lastmod` date is fixed to **14 May 2026** at [lib/seo.ts](/home/xwingace/Documents/Projects/Taco-upgrade/lib/seo.ts:7), and the live sitemap repeats it for all static routes. If those pages have changed since that date, the signal is stale; if they have not, it is valid. Tie last-modified values to actual page/content edits, or omit them where trustworthy dates are unavailable. A sitemap is a discovery/canonical hint, not an indexing guarantee; list only URLs intended for search. [Google sitemap guidance](https://developers.google.com/search/docs/crawling-indexing/sitemaps/overview) and [canonical consolidation guidance](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls) (accessed 9 Oct 2026).

The implementation already uses Next App Router metadata, dynamic metadata for programmatic guides, and JSON-LD for Organization, WebSite, Article, BreadcrumbList, FAQPage, and SoftwareApplication. Next documents that route metadata is resolved into the initial response where statically renderable and supports per-route canonicals/robots; retain that server-rendered approach. [Next metadata API](https://nextjs.org/docs/app/api-reference/functions/generate-metadata) (accessed 9 Oct 2026). Google requires markup to match visible page content and makes no guarantee that valid markup produces a rich result. Google announced FAQ rich results would stop appearing in Search on 7 May 2026 and removed the FAQ feature documentation in June 2026; FAQ JSON-LD is not a Google growth priority here, though useful visible Q&A can remain for readers. [Google’s current Search documentation updates](https://developers.google.com/search/updates) (accessed 9 Oct 2026). Google’s current AI search guidance says there is no ideal page length, no need to “chunk” content, and no special markup required for AI search; focus on helpful original content for people. Thus the audit’s 250-word threshold is only a local review heuristic and must not trigger padding `/contact`. [Google AI search guide](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide) (accessed 9 Oct 2026).

## Explicit unknowns and hypotheses

- **Unknown:** Search Console index coverage, canonical selected by Google, impressions, clicks, crawl stats, and CrUX field performance. This review has no Search Console connector or export. Do not infer traffic, rankings, index counts, or keyword demand from the crawl.
- **Unknown:** whether `/suite` requires login before personalized data is returned. The request intentionally checked only the unauthenticated public response, not any user session. Verify the real access-control boundary separately.
- **Unknown:** whether the May 14 lastmod is stale relative to the deployed source content. The date is certainly fixed in source/live output; staleness depends on actual content changes.
- **Hypothesis:** sitemap and source match the currently deployed routes closely because all 35 listed URLs returned 200 and current route titles resemble source metadata. This is not a full artifact-to-deployment fingerprint.
- **Hypothesis:** privacy and terms were intended to be indexable, because they return public 200 and have descriptive metadata. If policy is to exclude them, apply deliberate noindex and still ensure the crawl can see it; do not canonicalize them to the homepage.
- **Not established:** SEO ranking benefit from adding page length, FAQ markup, or more JSON-LD. FAQ rich results are retired in Google Search. Treat content usefulness and truthful user value as the outcome; supported structured data can improve eligibility for specific rich results but does not promise rankings.

## Verification sequence for the later implementation

1. Run source-based route/metadata invariants and the expanded audit against the production host; assert only source facts that are deterministic.
2. Fetch every current sitemap URL and a maintained set of non-sitemap public/private routes. Check status, final URL, canonical, robots, and sitemap intent from server HTML.
3. Validate representative JSON-LD against visible page content and run Google’s Rich Results Test only for applicable supported features.
4. Review Search Console URL Inspection, Page Indexing, Sitemaps, and Core Web Vitals reports after deployment. Do not claim indexing or performance outcomes from HTTP checks alone.
