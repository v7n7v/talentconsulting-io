# Taco agent architecture audit — 2026-10-08

Scope: read-only audit of `/home/xwingace/Documents/Projects/Taco-upgrade`; no runtime or backend actions and no credential files inspected. Repository instructions read from `CLAUDE.md`. Source, not plans, is treated as ground truth. No implementation was changed.

## Findings

Taco already has useful pieces of an agent system, but its production career workflow is not an open-ended agent. The chat endpoint (`app/api/agent/chat/route.ts:527-555`) calls one OpenRouter model and executes model-selected tools in a bounded loop of at most four rounds. Its tool schemas are handwritten in `lib/assistant/tools.ts:24+`, with a switch-based executor at `:588-596`. This is genuine model-directed tool use, but authorization is uneven across tool executors: for example, `queue_application` accepts a model-provided confirmation boolean before writing an item to Taco's internal review queue (`lib/assistant/tools.ts:1005-1012,1039-1059`). That queue write does not submit an application externally. The calls are not streamed, and tool calls in each round run sequentially. The endpoint sends `qwen/qwen3.6-plus` directly (`app/api/agent/chat/route.ts:44-46,623-640`).

The more consequential career flow, `runSonaAgentHarness` (`lib/assistant/agent-harness.ts:475+`), is a deterministic workflow with one LLM-assisted goal parse, fixed search/rank/prepare/notify steps, and bounded outputs. It fetches sources, applies filters and eligibility gates, invokes resume morph/cover-letter generation, applies truth guardrails, writes review queue artifacts, records economics, and may notify. See goal interpretation at `:270-325`, fixed stages/search at `:713-809`, preparation and guardrails at `:926-1053`, and completion/notification/economics at `:1084-1172`. Do not describe this harness as autonomous planning or adaptive execution.

There is no GPT-6 Luna runtime/model route or fanout coordinator in the inspected source. The product registry in `lib/ai/providers.ts:1-21` configures Groq, OpenRouter, and Google; `lib/ai/models.ts:1-30` maps `sona` to Qwen. `package.json:94-107` includes AI SDK, Google, and OpenAI-compatible providers, but no first-party OpenAI provider dependency. “Luna” references in `.codex/long-horizon/taco-upgrade.md` describe development subagents and do not route Taco production requests or establish GPT-6 Luna API availability. The requested model ID/provider should be validated against the account’s supported API before coding; the repository alone does not establish it.

Useful reusable seams already exist: `SonaCapability` catalog and approval metadata (`lib/assistant/capabilities.ts:1-20`), page/job/resume execution context (`lib/assistant/execution-context.ts`), model abstraction (`lib/ai/sdk.ts:7-80`), injectable harness dependencies (`lib/assistant/agent-harness.ts:453-500`), workload reservations and accounting (`lib/assistant/workload-policy.ts:13-20,57-76`; `lib/assistant/workload-reservation.ts:24-72`), activation receipts (`lib/assistant/activation-receipt.ts`), chat request idempotency (`lib/assistant/chat-message-quota.ts`), career-twin memory (`lib/career-twin.ts:44-104`), and evidence-rich queue contracts (`lib/assistant/harness-evidence.ts:30-87`). The `lib/sona/*` modules are mostly deprecated re-export aliases to `lib/assistant/*` (for example `lib/sona/agent-harness.ts:1-2`); new code should use `lib/assistant/*`.

## Current request and background flows

**Chat:** authenticated/rate-limited POST → Firestore request reservation/fingerprint → load selected resume, Career Twin and context → deterministic keyword capability/action plan → either receipt-gated harness invocation or model chat with tool calls → persist user/assistant messages → stage response and finalize reservation. Relevant code: `app/api/agent/chat/route.ts:288-318,320-420,527-580`; reservation/replay logic: `lib/assistant/chat-message-quota.ts:1-83`. The endpoint’s file header says “Streaming” (`:4`), but POST actually buffers JSON and returns a `Response` after model/tool work (`:304-312,527-580`); this should not be counted as streaming behavior.

**Interactive harness:** preflight validates inputs and issues a short-lived signed receipt (`app/api/agent/harness/preflight/route.ts:38+`; `lib/assistant/activation-receipt.ts`); harness route verifies and consumes that single-use receipt before calling the shared workflow (`app/api/agent/harness/route.ts:16-58`). This is a strong explicit-start and replay boundary. In chat, `run_career_goal_harness` also refuses execution unless `activationConfirmed` is true (`lib/assistant/tools.ts:708-718`).

**Harness workflow:** loads user preferences and a verified resume; resolves target and tier/mode; enforces paid/free workload reservations; records a run; interprets the goal with Groq JSON; performs up to four searches based on a fixed role/location combination; filters and ranks results; conditionally generates assets; saves queue records and evidence, then sends notification/digest subject to preferences. It is substantially scripted: model output does not choose the next action or tool, and the plan has fixed stages (`agent-harness.ts:713-809,926-1017,1053-1172`).

**Scheduled workflow:** `/api/cron/agent-pipeline` selects a bounded batch of users, checks tier/preferences, reads Career Twin memory, reserves workload, searches a fixed set of role/location combinations, scores and prepares eligible recommendations, and writes queue/evidence records (`app/api/cron/agent-pipeline/route.ts:95-180,204-255,286-350`). This is proactive automation, but still a deterministic cron pipeline, not a model-directed agent loop.

## What is already agentic vs. scripted

- **Agentic today:** chat model may choose from the declared tools; tool results return to the model for up to four rounds. Model decides whether/how to invoke available tools.
- **Scripted today:** capability choice (`createSonaActionPlan`) uses keyword matching (`lib/assistant/context.ts:64-75,135-147`); the career harness and nightly pipeline have fixed steps, fixed fanout counts, fixed loop order, and fixed eligibility gates.
- **Not present:** GPT-6 Luna model selection, multi-agent fanout/join, durable task graph, per-step checkpoints/resume, general cancellation propagation, a common typed tool registry with generated schemas/authorization, or an agent event stream. Run records do persist coarse steps/status, which is a useful starting point.

## Critical gaps for a fully agentic design

1. **No centralized model routing.** Chat hardcodes Qwen and harness/writing paths call Groq helpers directly; the registry and AI SDK bridge coexist with direct clients. GPT-6 Luna would require an explicit provider/model adapter and migration of these call sites, plus recorded model/version metadata. Avoid a broad global swap: route by task through an injected `ModelRouter`.
2. **Fanout must be planned, not implied by `Promise.all`.** Current workload envelopes count model calls (`workload-policy.ts:13-20,64-76`) and harness actual-work accounting currently tracks search/morph/cover-letter/digest work; any Luna worker fanout needs explicit worker/call/token/time ceilings and a reservation formula before launch. Parallelize only independent read-only analyses at first. Do not concurrently mutate Firestore or issue email/queue writes from workers.
3. **Approval checks are not yet a robust tool authorization layer.** Chat prompts require explicit approval, but `queue_application` checks a model-provided `args.userConfirmed` boolean (`lib/assistant/tools.ts:1005-1012`). The harness’s signed, user-bound, one-use activation receipt is a stronger pattern. All write-capable tools should receive server-derived authorization context/approval receipt, with schemas and permissions validated before executor invocation; model arguments alone must not authorize mutation.
4. **Cancellation and deadlines do not cross the workflow boundary.** Chat model fetch has a 45-second timeout (`app/api/agent/chat/route.ts:623-640`) but no request-signal propagation into tools; the harness has a 10-minute stale running-lock (`workload-reservation.ts:43-50`) and compensation helpers but no user cancellation token or per-step checkpoint. AI SDK bridge functions currently expose no `AbortSignal` (`lib/ai/sdk.ts:13-29,35-43`). Add a run-scoped `AbortSignal`, deadline, and checkpoint contract before parallel calls.
5. **Recovery exists, but not full durable orchestration.** Chat request receipts make duplicate sends/replays safer (`chat-message-quota.ts:34-83`); harness records coarse run progress and reconciles failed workload reservations (`agent-harness.ts:723-761,812+`). For arbitrary agent execution, persist planned steps, worker IDs, inputs/hashes, status, attempts, timestamps and outputs before/after each side effect. Use idempotency keys and an outbox for all mutations and notifications.
6. **Evidence and memory are useful but mixed-trust.** Career Twin is a structured derived summary (`career-twin.ts:44-104`) and prompt context combines twin, resume, application, job context, stories, and chat (`assistant/context.ts:85-132`). Queue artifacts carry fit/risk/source evidence (`harness-evidence.ts:30-75,97-141`). Extend to typed evidence references (source record/version/hash, observed-at, confidence/status) so a fanout worker cites source facts and unknown remains distinct from zero. Do not let model summaries become source-of-truth memory without provenance and user correction path.
7. **Tool surface is duplicated and too broad for unconstrained model access.** `SONA_TOOLS` schemas and `executeTool` switch are separate, while API routes independently implement many capabilities. Add one typed registry with input/output schemas, read/write classification, tier policy, approval policy, idempotency behavior, and timeout. Let the planner see only tools authorized for this run.

## Recommended architecture and first vertical slice

Use one server-owned orchestrator with a typed run contract, a model router, a read-only planner/fanout phase, deterministic policy checks, and a serialized commit phase. “Agentic” should mean the model chooses among bounded, observable steps; code remains authoritative for identity, allowed tools, budget, approval, truth checks, and writes. GPT-6 Luna can be the planner/worker model once its production API path is confirmed. Fanout returns structured proposals with evidence references; a join/critic reconciles disagreements and missing evidence before any write.

**Experimental first slice: a read-only “analyze this role” chat run with bounded Luna fanout, contingent on confirming product GPT-6 Luna API availability.** Trigger from the existing `oracle.decide_strategy` capability and explicit job context. Keep the current user-authenticated chat reservation and conversation store. The orchestrator creates two independent read-only tasks: (a) resume-to-JD evidence/fit analysis using verified resume + supplied posting; (b) posting/source/risk and compensation extraction from supplied job data. Join into a typed result, validate all claims against source evidence, then return a recommendation and gaps. No queue, email, resume-version or application write in this slice. Log parent and child run records, model IDs, budget consumption, evidence IDs, cancellation and terminal status. This exercises model routing, fanout/join, durable status and evidence while avoiding the harness’s expensive write path.

Suggested interfaces/modules (new names are proposals, not existing code):

- `lib/assistant/runtime/types.ts`: `AgentRunRequest`, `AgentRunContext` (uid/tier/capability/approval/runId/deadline/signal), `AgentTask`, `AgentTaskResult`, `EvidenceRef`, `AgentRunEvent`, terminal states.
- `lib/ai/model-router.ts`: `ModelRouter.runStructured({task, schema, modelProfile, signal, maxOutputTokens})`; map `planner/worker/critic` to GPT-6 Luna after provider validation; injectable fake in tests.
- `lib/assistant/runtime/registry.ts`: typed tool registry; each definition owns Zod input/output schemas, read/write class, entitlement, approval mode, timeout, idempotency key strategy and executor.
- `lib/assistant/runtime/orchestrator.ts`: plan → authorize/budget → bounded `Promise.all` read-only tasks → validate/join → persist run state/events → response; all mutations serialized through approved tools.
- `lib/assistant/runtime/store.ts`: Firestore adapter for parent/child run, checkpoints, evidence refs and lease/heartbeat; do not persist raw secrets or unbounded prompt dumps.
- First route integration: `app/api/agent/chat/route.ts` delegates only the selected read-only capability to the runtime; retain existing route auth, chat request idempotency and UI response contract.

After the first slice, migrate harness goal understanding/search in phases, preserving the existing deterministic eligibility and truth-guard checks as policy tools. Introduce write-capable tools only after receipt-bound approvals, run cancellation and idempotent outbox commits are end-to-end. Keep cron as a trigger that enqueues the same durable run type rather than maintaining a second agent implementation.
