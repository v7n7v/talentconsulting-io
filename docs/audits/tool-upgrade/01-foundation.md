# Foundation tools: source audit and upgrade recommendations

Audit date: 2026-09-28. Scope: `/suite`, `/suite/agent`, `/suite/resume`, `/suite/ats-analyzer` and aliases, `/suite/cover-letter`, `/suite/linkedin`, and their principal client/server contracts. This report is source inspection in `Taco-upgrade`; it is not a claim of live provider validation, a security penetration test, or a usability study with participants. No application files were changed and no live accounts, credentials, model providers, billing, or external services were exercised. Existing tests were read as evidence of intended coverage, not re-run here. The parent audit owns browser observations.

**Decision:** keep the foundation, but finish the source/context/output contract before expanding tools. The strongest implementation is the guarded resume intake/review/export path. The weakest seams are shared context ownership, legacy writing endpoints, and claims that imply more verification than the underlying checks establish. No P0 incident was established. P1 below means fix before a broader real-data trial; P2 means workflow/clarity improvement that can follow the common foundation.

## Cross-tool findings requiring first implementation work

### F01 — P1: account and revision ownership is incomplete outside the core resume intake

**Observed code:** `lib/application-kit.ts:4,15-31,75-101` persists contact/resume snapshot, job details and output under one `talent-application-kit-context` key, with no owner or input revision. `hooks/useApplicationKitContext.ts:11-27` loads it once and shallow-merges against the hook's local state. It does not subscribe to other instances or authentication changes. Sidebar sign-out only clears job caches before signing out (`components/SuiteSidebar.tsx:489-497`); auth helper does not clear the kit (`lib/firebase.ts:218-226`). No kit clearing call was found in the scoped repository search.

Consumers hydrate old successful outputs (`app/suite/cover-letter/page.tsx:302-313`; `app/suite/linkedin/page.tsx:119-130`; `components/ATSScorePanel.tsx:360-365`). `resumeVersionToApplicationKitContext` updates source fields without clearing ATS/writing outputs (`lib/application-kit.ts:103-112`). Cover/LinkedIn also still read `talent-resume-draft` (`cover-letter:315-369`; `linkedin:132-161`), while Resume Studio now writes `talent-resume-draft:<uid>` (`lib/resume-intake.ts:31`; `app/suite/resume/page.tsx:743-812,992-1022`). Their legacy readers are therefore not reliable current-draft handoffs.

**Consequence/inference:** on a shared browser tab a later signed-in account can inherit the prior account’s kit state; source/target edits can retain a result generated against different evidence. Separate kit hooks in analyzer parent and child may overwrite one another's updates. This is a source-demonstrated design gap, not a live account-switch reproduction in this audit.

**Upgrade:** a single owner-scoped workspace context with explicit selected source version, source hash, target/application ID, target hash, generation operation ID and freshness status. Quarantine unowned legacy state rather than silently assigning it to the next user. Reset dependent output on source/target changes; serialize/persist through one store with subscriptions. Use current data to avoid shallow merge races.

**Acceptance:** tests for A→sign out→B, late request from A, tab reload, competing context updates, storage disabled/quota failure, source replacement and target replacement. No data/result from A renders for B; no stale result is exportable as current; every result shows exact input provenance; failed persistence is recoverable.

### F02 — P1: privacy and save copy contradict actual behavior

**Observed code:** Resume Studio’s source footer always says “Your files stay private on this device.” (`app/suite/resume/page.tsx:2809-2813`), and library rows say “Saved locally” (`:2785`). The client posts extracted resume text to the parse route (`:1110-1122`); that route sends it to Groq (`app/api/resume/parse/route.ts:28-54`). Saving uses the resume library/database, not only sessionStorage (`app/suite/resume/page.tsx:1434-1444`). Guest drafts are not persisted by the current owner-scoped session key (`:747,995`).

**Upgrade:** separate “Draft saved in this tab”, “Saved to your account”, “Not saved”, and “AI processing” copy, computed from actual state. Explain processing at upload before submission in normal product language.

**Acceptance:** guest, authenticated, parse in flight, save failure, remote save and local-storage failure each show a correct state. No device-only assurance appears on a cloud-processing flow.

### F03 — P1: Cover Letter proof is partly a presentation layer, not enforcement

**Observed code:** active Cover Letter endpoint uses auth and Standard gating but only checks truthiness of company/title, accepts arbitrary resume shape, falls back to latest-created saved version, and permits “No resume available — write a general cover letter” (`app/api/agent/cover-letter/route.ts:25-81,104-139`). Its source fallback only reads `e.bullets` and grouped skill items (`:70-75`), although canonical resumes use `achievements`; this can omit the strongest evidence. The client passes missing ATS keywords into the prompt as gaps “to address naturally” (`app/suite/cover-letter/page.tsx:451-479`).

The proof report maps a model `toneScore` to a score called **Draft trust** (`app/suite/cover-letter/page.tsx:187-192`) and labels missing terms as claims to “Block” (`:173-177`), but copy/save/export use the generated text without that block being enforced (`:767-777`). `guardOutput` in the endpoint is an anti-artifact writing filter, not this source-bound claim ledger (`app/api/agent/cover-letter/route.ts:131-138`).

**Upgrade:** converge the active UI with an evidence-bound artifact service and return an actual claim/check result. Existing deterministic letter guardrails elsewhere are a reusable baseline, not proof that this legacy endpoint already uses them. Replace trust percentage with checks that were actually performed. Preserve explicit outline mode if no resume exists.

**Acceptance:** unsupported named employer, credential, amount, percentage or skill is rejected/flagged before export; absent evidence never yields a positive verification badge; tone remains an optional style judgment; selected saved source uses canonical normalization including achievements; test every tone/structure against the same invariant contract.

### F04 — P1: LinkedIn generation lacks a source-preservation/output validation boundary

**Observed code:** active LinkedIn route accepts `headline/about/targetRole/resumeData` without a schema/minimum-evidence check (`app/api/agent/linkedin-optimize/route.ts:24-43`), uses latest-created resume fallback that ignores canonical `achievements` (`:45-63`), and returns model output directly (`:78-111`). The prompt asks for confidence and keyword optimization but does not enforce source-bound factual claims. The frontend encourages leaving inputs blank and enables Optimize with no minimum context (`app/suite/linkedin/page.tsx:291-319`), and copies model output (`:435-449`). Headline/About character-count presentation does not by itself establish output enforcement.

**Upgrade/acceptance:** normalize explicit source data, require enough evidence for any new biography, validate both request and output shape, enforce real character limits, reject unsupported facts and retain original text for review. Show “AI writing assessment” instead of implying a measured LinkedIn algorithm score. Use role positioning independent of transient application gaps. Returned malformed arrays/sections must render a recoverable error, not a component exception.

### F05 — P1: Ask Taco’s “session/check-in” allowance is charged per successful response

**Observed code:** Standard allows one weekly count and Free two lifetime counts (`app/api/agent/chat/route.ts:177-205`). The route increments after each successful ordinary message (`:603-609`) and successful harness result (`:513-519`), using read-then-write counts (`:208-230`) rather than a reservation/idempotent operation. Conversation ID does not exempt follow-up messages. This is a mismatch with error copy describing “weekly check-in” and “demo sessions”, even if per-message charging was once intended.

**Upgrade:** explicitly define a check-in window or rename allowance as responses; recommend one outcome-focused session permitting the clarification required to finish. Apply atomic usage reservation plus idempotent completion tied to an operation ID; failed requests should not double-charge on retry. Show remaining allowance before work starts.

**Acceptance:** a two-turn clarification completes within the intended session; multiple tabs cannot overspend/undercount; timeout→retry counts once; a no-op/no-evidence response is handled according to an explicit documented policy. Validate this separately from model quality.

### F06 — P1: stale asynchronous UI results can land in a different account/conversation

**Observed code:** Ask Taco invalidates intake on user change but does not clear messages, active resume, selected conversation or history there (`app/suite/agent/page.tsx:921-929`). History loads and chat responses write unconditionally (`:1117-1162,1248-1262`). Starting another conversation while a request resolves lacks an operation binding at those setters (`:1128-1134`). Cover/LinkedIn generation and saved-letter/resume list loads similarly lack current-owner/request guards (`app/suite/cover-letter/page.tsx:372-376,451-494`; `app/suite/linkedin/page.tsx:163-199`; `components/ATSScorePanel.tsx:375-382,405-449`). ATS Preview's latest-resume fetch can replace a user-selected source (`app/suite/ats-preview/ATSPreviewContent.tsx:274-299`).

**Upgrade/acceptance:** use the stronger intake lifecycle pattern across tools. Operation identity must bind owner, selected input revision and destination conversation. Cancel or ignore stale completion; clear sensitive visible state on owner change; preserve unsent draft; test rapid history switching and selected-source changes while fetches resolve in reverse order. This is distinct from server authorization: it is a frontend lifecycle/data-mixing risk.

### F07 — P1: the ATS family mixes separate assessments under one implied authority

**Observed code:** Preview is a client heuristic over normalized JSON (`app/suite/ats-preview/ATSPreviewContent.tsx:51-143`), with a 1.5 second cosmetic processing delay (`:301-321`) and vendor-branded confidence. It never uploads the exported PDF/DOCX to those vendors. Quality Scan asks Gemini how well plain text “passes ATS parsing” (`app/api/resume/check/route.ts:49-75`). Match Score is a deterministic weighted lexical/formatting estimate, with overall numeric value floored to 5 and capped to 98 (`lib/ats-score.ts:376-395`), and already states “Estimated match, not a measured outcome” (`components/ATSScorePanel.tsx:570-572`). Resume workbench labels the mere presence of a proof score “Proof verified” (`components/resume-studio/ResumeReviewWorkbench.tsx:228-231`).

**Upgrade:** a shared “Checks” model with three separately named signals: exported-document extraction, requirement evidence coverage, and optional writing feedback. Drop unsupported vendor fidelity and guarantees; state what each signal can and cannot establish. For missing keywords, change automatic “Add these missing keywords” (`lib/ats-score.ts:400-403`) into evidence-seeking prompts.

**Acceptance:** a fixture with high keyword repetition but no qualifying experience cannot be called qualified; negative credentials remain negative; an empty requirement set is unassessed; arbitrary numeric floors cannot be presented as hiring likelihood; re-parse exported artifact, not only the internal JSON, for structural checks.

### F08 — P1: lossy Preview auto-fixes change shared evidence without a new revision

**Observed code:** Preview's “auto-fix” removes any unknown non-ASCII skill character, trims summary to ~95 words, and caps experience at six bullets (`app/suite/ats-preview/ATSPreviewContent.tsx:325-362`). It updates the shared resumeSnapshot while retaining previous kit fields/results (`:365-378`), including source version identity. These are real content changes, not just a rendering toggle.

**Upgrade/acceptance:** present proposed differences, identify potential lost content, preserve an immutable source, require explicit accept, create a derived draft revision and invalidate old checks. International names/skills, long summaries, seven-plus bullets, undo and cross-tool navigation must retain original evidence; no “fixed” claim is shown when a change was only simulated.

### F09 — P1/P2: draft/save/track and generation completion need durable explicit states

**Observed code:** Save & Track can save a resume and fail application creation, then clear draft and show the modal's success state (`app/suite/resume/page.tsx:1494-1538`). Download also clears draft (`:1748,1781`) without guaranteeing a cloud save. Cover letter reload restores text/company/title/style/JD but not selected source binding or proof metadata (`app/suite/cover-letter/page.tsx:426-440`); the next save takes the currently selected kit source (`:378-402`). This can associate an old letter with a newly selected source.

**Upgrade:** separately track draft saved, generated, reviewed, exported and application-linked. Save operations should carry idempotency keys and stable entity IDs. Reload restores the original provenance; changed source/target creates a new version.

**Acceptance:** partial tracking retry uses existing resume ID and creates only one application; save/load/re-save preserves letter/source association; successful local download never says cloud-saved; errors retain editable content with a concrete recovery action. Prioritize entity/provenance correctness P1, general convenience P2.

## Recommended implementation sequence for this group

1. **Shared ownership and truth contract (P1):** owner-scoped reactive context, immutable source/JD revisions, normalized canonical evidence, operation IDs, stale-result guards, honest save/privacy/verification copy. Migrate legacy local keys without assigning unknown ownership.
2. **Source-to-resume completion:** keep existing intake controls; make tailoring modes honest; bind review/export/save to the reviewed revision; fix partial Save & Track and explicitly separate optional rewriting from safe ordering. Add no-op behavior and artifact-extraction checks.
3. **Application writing:** one request/response schema and source resolver across manual and Taco-driven writing, real draft editor, claim checks, revisioned save, truthful model feedback. Cover Letter is the first role-bound writing artifact; LinkedIn follows with a separate career-positioning context.
4. **Consolidate checks and destinations:** make keyword coverage accessible within role review, move structural parsing checks into Resume Review, retire vendor-simulation promises, fix aliases/deep links, merge Blueprint into role preparation.
5. **Finish Ask Taco:** align check-in allowances, durable conversation/retry semantics, visible context, reliable history and voice recovery. Keep deterministic tools authoritative and user review explicit.
6. **Validate complete journeys before adding modes:** confirmed source → tailored reviewed version → real PDF/DOCX extraction → cover letter/save/load → application link; profile draft separately; account-switch and failure injection at each boundary. Browser usability checks should include keyboard, touch, small-screen and actual first-time task completion, not only route rendering.
